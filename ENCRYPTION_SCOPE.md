# At-rest encryption acceptance boundary

Updated 14 October 2026 after explicit cutover approval. Production now selects AES-256-GCM complete SQLite snapshots with a Windows current-user DPAPI-protected key. The selected directory is .aura-private/encryption-cutover-20261014. See AES256_POST_CUTOVER_AUDIT.md for validation and LEGACY_MATERIALS_RETAINED.md for the completed historical-material disposition.

The roadmap requires AES-256 coverage of retained application data. The historical Fernet stores protected selected fields with AES-128-CBC/HMAC but left metadata and vectors outside encryption. Active production now encrypts complete sessions, audits, identifiers, timestamps, memory content, embeddings, retrieval metadata and quota state. Source files, explicitly user-created output documents and user-controlled external apps are not implicitly encrypted by AURA. Temporary screenshots are held in memory unless explicitly saved.

Required protected set: complete session/audit records, memory content and embeddings with retrieval metadata, and communication-limit state. New runtime paths must remain ignored. Recovery copies of the previously exposed state are private forensic material and must remain separately controlled; new encryption cannot revoke historical exposure.

Implemented storage design: use an authenticated AES-256 envelope with a dedicated versioned key, encrypt complete records and vector snapshots, and keep a plaintext vector index only in process memory. Use atomic replacement for encrypted snapshots, authenticated version/record identity, unique nonces, bounded decoding, strict corruption failure and serialized writers. Persist audit/limit decisions durably before effects. For larger datasets, evaluate a supported encrypted database instead of claiming payload encryption covers page/WAL/index metadata.

Before switching retained data: create a hash-verified private backup; export/decrypt into memory; write a separate encrypted target; compare record counts and decrypted payload hashes without printing contents; test restart/retrieval, wrong-key and tampering rejection, crash recovery, quota persistence and plaintext-canary absence in all files including journals; then explicitly approve cutover. Preserve the old stores for rollback until acceptance and owner-approved retirement. Preparation created a dedicated DPAPI-protected AES key; production activation is complete; irreversible retirement has not occurred.

Threat model: disk disclosure while AURA is stopped is in scope. An attacker running as the same account while the key is unlocked, a local administrator or operator-approved disclosure is not defeated by application encryption. Whole-volume encryption may supplement this design, but its presence/configuration has not been verified and is not assumed.

Prepared evidence: complete AES-256-GCM snapshots cover records, metadata, vectors and quota state; plaintext SQLite and Chroma indexes remain in memory. Current-user DPAPI protects the dedicated key. Unit/integration tests cover restart, tamper/wrong-key rejection, concurrent writers, crash recovery, quota persistence, plaintext canaries and approval/audit ordering. The real retained-data rehearsal preserved all 3 sessions, 4 audits, 1 memory and 4 quota records, verified matching payload hashes and retrieval, and left the source untouched. See reports/encryption_cutover_preparation.json and the final regression report.
